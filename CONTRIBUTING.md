# Contributing

Thanks for taking an interest. This is a small, deliberately plain toolkit: standard library only, deterministic output, and documents that read as neutral practitioner guidance. Changes should keep it that way.

## Ground rules

1. **No real data, ever.** Do not commit extracts, screenshots or examples from a real organisation, and do not use real company, customer, supplier or person names. The examples are fictional and generated by a seeded script. New examples should use invented names, and tax numbers must be random digits.
2. **Standard library only** for the `erp_consol` package. Test tooling is fine under the `dev` extra.
3. **Deterministic output.** The same inputs must give byte-identical files. Sort anything whose order matters and never write timestamps into outputs.
4. **The tools suggest, people decide.** Do not add behaviour that approves a mapping, merges records or changes source data. Suggestions stay suggestions.
5. **Vendor neutral.** Say "ERP A", "ERP B" and "the target". Do not name products or quote vendor documents, prices, standards text or legal wording. If a document states a fact about a law or a format, say where and when it was checked.
6. **Not legal, tax or accounting advice.** Keep the scope notes in the documents.
7. **British English, plain tone, no long dashes.** A test fails if an em dash or en dash appears in any text file. Use commas, colons, full stops or brackets.
8. **Judgement is labelled as judgement.** Weights and thresholds are starting points. If you change one, change the documentation in `docs/scoring-models.md` or `docs/readiness-thresholds.md` in the same pull request and say why.

## Development setup

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
python -m pytest -q
```

## Changing behaviour

The files under `examples/data`, `examples/truth` and `examples/reports` are compared with a fresh run by the tests, so a behaviour change needs them regenerated in the same commit:

```bash
python examples/generate_examples.py
python examples/run_examples.py
python -m pytest -q
```

If figures in the README or the documents change, update them from the new output. Every figure in the documentation must come from a real run. Two tests assert numbers quoted in the documents: the suggester accuracy table and the headline duplicate counts.

## Changing the decision framework

Criteria, weights and scoring anchors are in `decision/criteria.csv`. Each criterion needs an axis (`case` or `ability`), a weight of 1 or more and anchors for scores 1, 3 and 5 that describe observable situations. Gates need an effect (`defer` or `cap_partial`). Update the tables in `decision/README.md` to match. A test checks that every id in the criteria file appears in that README.

The cut-offs (65, 60 and 40) are in `erp_consol/decision.py`.

## Diagrams

Diagrams are Mermaid sources in `docs/images/`. Render them with the Mermaid CLI and commit both files, then look at the result:

```bash
mmdc -i docs/images/toolkit-flow.mmd -o docs/images/toolkit-flow.svg
mmdc -i docs/images/approach-selection.mmd -o docs/images/approach-selection.svg
```

## Pull request checklist

- [ ] Tests added or updated and passing
- [ ] Examples regenerated if behaviour changed
- [ ] Documentation figures updated from real output
- [ ] No real names, data or credentials in the diff
- [ ] No long dashes, no product names, scope notes kept

## Reporting concerns

The tool reads local CSV and JSON files and makes no network calls. If you find a way for crafted input to cause harm, please open a private security advisory on the repository rather than a public issue.
